Create or update `ATOM.md` at the workspace root. ATOM injects this file into the system prompt of every agent
session in this project (truncated after 20,000 characters), so every line costs context in every
conversation. Make it concise, accurate and high-signal: the facts an expert agent needs and cannot cheaply
infer by looking around. Load the `atom:project-onboarding` skill with the Skill tool first - it is the process
for analyzing an unfamiliar repository, and its `templates/ATOM.md` is the starting skeleton.

Extra focus or notes from the user: $ARGUMENTS

## 1. Collect what already exists

- Read `ATOM.md` if present - you are updating it, not replacing it. Preserve what the user wrote, keep its
  intent, and change only what is missing, wrong or stale.
- Read other agent and contributor instructions: `CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.md`, `.cursorrules`,
  `.cursor/rules/`, `.github/copilot-instructions.md`, `CONTRIBUTING.md`, `README.md`. ATOM also loads
  `CLAUDE.md` automatically, so do not copy its content into `ATOM.md`; reference it or add only what is missing.

## 2. Analyze the repository

Use Glob, Grep and Read (delegate broad reconnaissance to the `atom:explorer` subagent if the repo is large):

- **Stack and tooling:** manifests (`package.json` and its lockfile to identify npm/pnpm/yarn/bun,
  `pyproject.toml`, `requirements*.txt`, `go.mod`, `Cargo.toml`, `Gemfile`, `pom.xml`), runtime versions
  (`engines`, `.nvmrc`, `.python-version`, `rust-toolchain.toml`, `go` directive).
- **Commands:** `package.json` scripts, `Makefile`, `justfile`, `Taskfile.yml`, `tox.ini`/`noxfile.py`,
  `docker-compose.yml`, and CI workflows (`.github/workflows/*.yml`) - CI shows the commands that actually gate
  merges. Find how to run a **single** test, not only the whole suite.
- **Architecture:** top-level directories and their roles, entry points (main files, servers, CLIs, workers),
  how the main pieces talk (HTTP, IPC, queues, database), where shared types or contracts live.
- **Conventions:** lint and format configs (`eslint`, `prettier`, `biome`, `ruff`, `black`, `gofmt`,
  `rustfmt`, `.editorconfig`), TypeScript strictness, test file location and naming, error-handling and logging
  patterns, commit style (`git log --oneline -n 20`), branch naming.
- **Gotchas:** required environment variables (`.env.example`), services that must be running, generated code
  that must not be edited by hand (and the command that regenerates it), unusual build steps, platform quirks,
  slow or flaky test suites, files marked "do not edit".

## 3. Verify the commands

Run the cheap, local commands that do not change state to confirm they work as written: typecheck, lint in check mode,
unit tests (for a big suite, a single test file is enough to prove the command shape). Ask with
AskUserQuestion before running anything slow, networked or stateful - dependency installs, database
migrations, Docker, deploys, end-to-end suites. If dependencies are not installed, do not install them unasked;
mark those commands as unverified. Never write a command into `ATOM.md` that you only guessed.

## 4. Write ATOM.md

Aim for roughly 40-150 lines. Use this shape, dropping sections that would be empty:

```markdown
# <Project name>

<One paragraph: what this project is, who uses it, the main technologies, how it runs or ships.>

## Commands

| Task | Command |
|---|---|
| Install | `pnpm install` |
| Dev | `pnpm dev` |
| Test (all) | `pnpm test` |
| Test (single) | `pnpm vitest run src/cart/total.test.ts -t "discount"` |
| Typecheck | `pnpm typecheck` |
| Lint / format | `pnpm lint` / `pnpm format` |
| Build | `pnpm build` |

## Architecture

- `src/server/` — HTTP API (Fastify); routes in `routes/`, business logic in `services/`
- `src/web/` — React SPA; talks to the API only through `src/web/api/client.ts`
- `packages/shared/` — zod schemas shared by server and web; change these first when a contract changes

## Conventions

- Validate all request input with the zod schemas in `packages/shared/schemas/`; never trust `req.body` directly.
- Tests live next to the code as `*.test.ts`; use the factories in `test/factories/` instead of literal fixtures.
- Errors: throw `AppError` subclasses from `src/server/errors.ts`; the error middleware maps them to responses.

## Gotchas

- `src/server/db/generated/` is generated by `pnpm db:generate` — never edit by hand.
- Integration tests need Postgres: `docker compose up -d db` first.
```

Writing rules:

- Specific and imperative ("Use `AppError` subclasses from `src/server/errors.ts`"), never generic advice
  ("write clean code", "add tests") - the agent already knows that.
- Every path must exist and every command must be one you verified or clearly mark as unverified.
- No secrets, tokens, internal URLs or personal data.
- No exhaustive file listings or duplicated README prose; link to docs for depth.
- Incorporate the user's focus notes from above where they belong.

When updating an existing `ATOM.md`, edit it surgically with Edit rather than rewriting it wholesale.

## 5. Report

Summarize what you created or changed (sections added, facts corrected), which commands you verified and how,
which you could not verify, and any questions where the code was ambiguous - for example two competing test
commands or an unclear deployment target.
